## 1. 背景与动机

### 1.1 已有积累

「播客抄袭鉴定」项目在 2026 年 8 月完成了一个 75 组对照的阶段性核查，其核心资产不是结论本身，而是被验证有效的一套**核查方法论**：

- **E1–E5 证据分级体系**：从"主题相同"（E1，弱）到"错误传播"（E4，极强）的五级证据强度刻度，抄袭/洗稿认定必须多层证据叠加，单层相似不构成结论；
- **细节指纹（fingerprint）方法**：用冷门、具体、可独立验证的内容点（独特案例、数据、口误、冷知识、"卫生法庭"式怪词）做同源判定；
- **四步工作流**：建库 → 跨语言初筛（embedding 余弦）→ 深查（转录+指纹+结构对齐）→ 报告（独立模型复核）；
- **措辞纪律**：区分「实锤/疑似」而非直接说「抄袭」，不做动机推断，所有引用可回溯（原文引用+URL+时间戳）。

但该流程以一次性 Python 脚本形式存在，每查一期都要人工跑十余个脚本，门槛高、无法复用给社区。

### 1.2 市场空白

现有的相似度工具都不覆盖这个场景：

- 学术查重（知网/Turnitin）：同语言、纯文本、封闭库，无法做中英跨语言、播客音频、文化内容的"洗稿"鉴定；
- AI 检测工具（GPTZero 等）：检测"是否 AI 生成"，不是"是否抄袭他人"；
- 事实核查平台（Snopes/腾讯较真）：验证事实真伪，不验证内容归属。

「一段中文内容是否抄袭/搬运/洗稿了一段外文内容」这件事，目前只有人肉+AI 的临时工做法，没有产品化。

### 1.3 产品定位（一句话）

**卫生法庭是一个半娱乐半严肃的交互式网页法庭：用户提交一段文化内容（链接或文本），法庭依照司法级证据规程完成取证、侦查、检索、对质、宣判，最终给出「卫生 / 可能不卫生 / 不卫生」的裁决与可复核的判决书。**

- "半娱乐"=《大逆转裁判》式的法庭戏剧包装（异议！、判决锤、证物牌）；
- "半严肃"= 背后是 E1–E5 证据分级 + 指纹比对 + 结构对齐的完整算法框架，结论措辞克制、全程可复核。

### 1.4 设计公理：机制严谨 × 呈现漫画（第一原则）

产品的两层人格严格分层，任何一层不得侵入另一层：

**内核层（机制与算法）——绝对严谨**

- 证据分级、指纹验证、结构对齐、裁决阈值全部由确定性规则驱动，逻辑可审计、结果可复现；
- 引文必须通过子串定位校验，杜绝幻觉证据进入判决书；
- 措辞纪律（不用指控性词汇、不做动机推断、区分「未发现」与「清白」）是不可协商的硬约束；
- 娱乐元素（连击、吐槽、动画强度）只读取裁决结果用于演出，**从不参与**任何证据评级与裁决计算。

**外观层（视觉与演出）——彻底漫画化**

- 界面语言全面采用《大逆转裁判》式漫画语汇：漫画分格、集中线、速度线、拟声词演出（异议！/ガーン！/ドン！）、夸张的证物牌与印章动画；
- 娱乐只发生在「怎么说」，从不发生在「说什么」：吐槽与戏谑只存在于演出层（动画字幕、旁白气泡），判决书正文措辞保持克制；
- 漫画化 ≠ 暗黑化：采用明亮饱和的漫画配色，仍禁暗色赛博底与霓虹渐变（用户既有偏好不变）。

**一句话检验标准**：把所有动画、音效、漫画元素全部关掉，产品退化为一个严肃的核查工具，且每一份判决与之相比一字不差。

### 1.5 与前序项目的关系

| 项目 | 角色 |
|---|---|
| 播客抄袭鉴定 | 方法论母体：算法框架与证据分级的来源；其已产出的 75 组对照可成为卫生法庭的种子案例库 |
| fact-check | 工程母体：React+Vite+TS+BYOK 的产品形态、严格 JSON Schema 输出、多层限流、server 代理模式 |
| 卫生法庭 | 面向公众的产品化：把脚本流程变成任何人在浏览器里都能走完的开庭流程 |

## 2. 目标与非目标

### 2.1 产品目标

1. **G1 流程产品化**：把"元信息整理 → 多轮搜索 → 比对核查 → 裁决"固化为一条网页交互流程，普通用户零脚本门槛；
2. **G2 判决可信**：每份判决书附完整证据链（双方引文、来源 URL、抓取时间、证据等级、复核意见），第三方可复核；
3. **G3 零门槛部署**：核心版本纯静态托管（GitHub Pages），用户自带 API Key（BYOK），无服务器成本；
4. **G4 可扩展的模型接入**：用户可接入自己的 API 与模型（GLM/Gemini/OpenAI 兼容端点等），默认配置开箱即用；
5. **G5 社区参与**：评论信号（"群众线报"）成为正规证据来源；判决书可分享、可沉淀为公共案例库。

### 2.2 非目标（明确不做）

- **不做法律结论**：不使用"侵权/违法/抄袭罪"等法律定性词汇，不推断主观动机；
- **不做全量普查**：不做"扫描某播客全部 349 期"式的批量任务（那是母项目脚本的事）；
- **不做内容存档/盗版库**：不系统性存储受版权保护的完整原文，只保存比对所必需的引用片段；
- **v1 不做音频转录**：浏览器直连 ASR 的通道实测不通（见附录 A），音频转录推迟到 v2 后端；
- **不做自动举报/维权**：输出仅为文本证据分析，不代用户发起任何平台动作；
- **不做 AI 文风检测**（2026-08-19 拍板）：Pangram 类工具存在假阳/假阴，风格概率不构成司法级证据；本庭只采痕迹证据（对齐段/错误传播/不可靠性标记），见机制 PRD §2.4。

## 3. 目标用户与场景

| 用户 | 场景 | 核心诉求 |
|---|---|---|
| 社区核查志愿者 | 在豆瓣/小红书看到对某期播客的抄袭质疑，想自己验证 | 不用装 Python 环境就能跑完整核查流程，拿到可贴回帖子的判决书 |
| 普通读者/听众 | 读到一篇"知识密度异常"的文章，隐约觉得像翻译腔搬运 | 丢个链接，3 分钟内知道"卫生不卫生" |
| 内容创作者 | 发布前自检：我的稿子会不会撞上已有英文源 | 主动送检，避免事后被锤 |
| 研究者/媒体 | 观察某个内容账号的"卫生记录" | 查阅历史判例、引用证据链 |

### 典型用户故事

**US-01**：网友在豆瓣看到有人质疑第 310 期播客。他打开卫生法庭，粘贴小宇宙链接。法庭渲染出法庭界面，依次播放"立案→侦查→检索→对质"的推进动画。当指纹比对到「卫生法庭 corps→court」时，屏幕砸出"异议！"。最终判决书盖章「不卫生（E4 错误传播）」，附双方引文与原始链接。他把判决书截图贴回豆瓣。

**US-02**：用户提交一篇微信公众号文章。侦查阶段法庭提取出 6 个指纹候选。检索阶段只找到 1 个弱候选源。宣判为「休庭（证据不足）」，判决书说明"已核查 N 个指纹，均未命中现有可检索源"，并注明这不等于证明清白。

**US-03**：用户提交一本付费书籍的章节摘录（手工粘贴文本）。因无法获得候选原文全文，法庭进入降级流程：仅基于公开书评、试读章节与元信息做有限比对，判决书标注「证据等级受限」。

## 4. 核心概念与裁决体系

### 4.1 证据分级（继承母项目，一字不改）

| 级别 | 证据类型 | 说明 | 单独效力 |
|---|---|---|---|
| E1 | 主题相同 | 都讲同一事件/人物 | 弱（公共素材） |
| E2 | 结构相同 | 章节、叙事顺序、详略取舍一致 | 中 |
| E3 | 细节指纹 | 相同的独特细节：冷门案例、数据、类比、口误、例证组合 | 强 |
| E4 | 错误传播 | 原文的事实错误/非常规解读（含机器转录错误）被复制 | 极强（几乎排除巧合） |
| E5 | 翻译腔/措辞 | 中文表述是英文原句的直译腔 | 中（需多例） |

指纹筛选标准（"卫生法庭式指纹"）：非教科书常识、具体到可检索（专名/数字/日期/轶事）、可组合（同集 ≥3 个指纹同命中则巧合概率急剧下降）。

### 4.2 裁决词表（游戏化用词 × 严格映射）

**原则：游戏化只做视觉与词汇包装，判定逻辑与阈值由证据分级严格驱动；所有判决书底部固定免责声明。**

| 裁决 | 触发条件（算法阈值） | 对应母项目旧词 | 判决书话术 |
|---|---|---|---|
| **不卫生** 🔴 | E4 命中，或 E2+≥3 个 E3 指纹同时命中 | 高度吻合 | "本庭认定该内容存在明确的来源依赖痕迹，且未完成来源标注义务" |
| **可能不卫生** 🟡 | E1+E2，或 1–2 个 E3 指纹命中 | 部分吻合/疑似 | "本庭发现值得注意的相似信号，但现有证据不足以排除巧合或公共素材" |
| **卫生** 🟢 | 完成对质流程且指纹未命中，或署名完整 | 暂未发现/署名完整 | "就本案核查范围内，未发现来源依赖痕迹"（注明核查范围与局限） |
| **休庭** ⚪ | 内容不可得（付费墙/无转录/无候选源），或检索后证据不足 | 来源待定位 | "本案证据不足，休庭待查"——明确说明缺什么、用户可补充什么 |
| **不予受理** ⚫ | 输入不构成可核查的文化内容（纯图片描述缺失、文本过短等） | — | 程序性驳回，说明原因 |

措辞红线（写入 prompt 的硬约束）：不使用"抄袭/剽窃/盗窃/罪犯"；不推断动机（不说"故意""明知"）；区分"未发现"与"证明清白"；恒定附带"本判决为文本证据分析，非法律结论"。

### 4.3 "异议！"时刻（产品signature）

指纹命中（尤其 E4）时触发的游戏化高光动画——盖因为"卫生法庭"这个项目本身就诞生于一次指纹命中。这是产品情绪曲线的峰值，设计规范见 §8。

## 5. 产品流程：开庭五阶段

```
立案 → 侦查 → 检索 → 对质 → 宣判
（贯穿：群众线报通道、降级链、案件档案）
```

### 5.1 阶段一：立案（Case Filing）

**输入**：一个 URL（首选）或一段粘贴文本。

**立案门槛（2026-08-18 用户拍板）**：评定对象必须是**相对独立、自身完整的文化内容整体**——文字内容不少于 500 字，或音频时长不少于 5 分钟。片段、摘要、单条评论不足以构成评定对象，程序性「不予受理」；评论区与其他意外发现只能作为**已有案件**的补充线索与证据细节，不单独开庭。

**取证（Fetch Evidence）**：
1. URL 经 r.jina.ai 渲染抓取（免费无 Key 通道，实测支持 CORS 与小宇宙页面，见附录 A）；
2. 解析出**案卷（Case File）**：标题 / 作者 / 发布时间 / 正文或 shownotes /（小宇宙等平台）页内评论；
3. 内容类型识别：图文文章 / 播客单集（有音频无文稿）/ 已有转录稿的播客（PodScript、Apple Podcasts 转录页）/ 视频页面；
4. 播客单集且无现成转录：v1 提示用户粘贴转录稿或提供 PodScript 链接；拒绝则走「休庭」或"仅基于 shownotes 的降级核查"；
5. 取证结果与原文快照（截断哈希）存入案件档案——**证据固定**是后续一切可信度的基石。

**输出**：结构化案卷 JSON + 取证日志（URL、抓取时间、内容长度、降级原因若有）。

### 5.2 阶段二：侦查（Investigation）

两次 LLM 分析（单模型即可执行）：

**A. 案情画像（Profile）**：主题域、核心论点、叙事结构大纲（章节化）、关键实体（人名/书名/事件/数据）、语言特征（翻译腔信号）。这份画像同时服务于后续检索的 query 构造与判决书的"案情摘要"栏。

**B. 指纹候选提取（Fingerprint Candidates）**：从案卷提取 5–10 个 E3/E4 候选点，每个候选包含：类型标注（冷门案例/数据组合/怪词/类比/口误）、原文引文、检索用关键词组（中文+自动英译）。"卫生法庭"式的**无法解释的怪词**是最高优先级候选——它是 E4 的头号嫌疑。

**C. 群众线报（Community Leads）** ★本产品新增通道：提取单集/文章页内评论，识别"来源怀疑类"信号——
- 明示型："这不就是翻译了 XX 吗""来源呢""洗稿实锤"；
- 晦涩型："卫生法庭是什么鬼""没听说过这个机构""这个词好奇怪"（对陌生说法的困惑往往正是 E4 指纹的群众感知）；
- 多条评论指向同一内容点时聚合成一条线报，转化为定向检索 query。

群众线报不直接参与判级（避免舆论污染证据），只作为**检索线索与指纹候选补充**进入下一阶段；但在判决书中单列"群众线报"栏呈现——这与母项目"豆瓣帖线索"的角色完全一致，是把它制度化了。

### 5.3 阶段三：检索（Discovery）

多轮搜索策略（每轮产出候选源清单：标题/URL/日期/摘要）：

| 轮次 | Query 构造 | 目标 |
|---|---|---|
| R1 主题检索 | 案情画像的主题域+核心实体，英文为主 | 圈定同题材的境外播客/文章/书籍 |
| R2 指纹检索 | 每个指纹候选的精确短语（英译版），加引号精确匹配 | 直接命中候选原文 |
| R3 线报检索 | 群众线报提到的具体说法/人名/节目名 | 验证或排除社区指认 |
| R4 补充检索 | 对质阶段未命中时的换词重试（同义词、事件别名） | 提高召回 |

搜索通道优先级（BYOK 环境实测约束见附录 A）：
1. **GLM 内置 web_search 工具**（bigmodel chat completions 原生支持，CORS 已验证）——默认供应商时的首选，一次调用完成搜索+综合；
2. **s.jina.ai 搜索**（用户自配 Jina Key 时可用，CORS 开放）；
3. **降级**：用户模型无搜索能力时，提示配置或进入"仅对质用户提供的候选源"模式。

**时间方向过滤**：候选源发布时间早于目标内容的时间加权保留；晚于的标记为"反向可能"（目标反而是源）——这在上游数据混乱时是救命规则（母项目 v11 曾因时代错位产生假阳性）。

**候选源抓取**：Top N（默认 5）候选经 r.jina.ai 抓取全文入卷。付费墙内容拿不到全文时标记"部分取证"，进入降级对质。

### 5.4 阶段四：对质（Cross-Examination）

对每个"目标×候选源"对执行三层比对，产出证据项列表：

1. **结构对齐**：LLM 段落级语义对齐（移植 llm_align.py 的提示词设计：中文 ~600 字段 × 英文 ~1200 字段，逐段给对应关系+置信度+双方摘录），辅以叙事顺序的秩相关检验（移植 align_order.py 思路，LLM 输出的章节序列做 Spearman）；命中 E2 信号。
2. **指纹验证**：逐个指纹候选到候选源全文中验证（引文定位+LLM 判断语义等价）；移植 fingerprint_check.py 的"任一关键词命中即进入人工复核"思想，但全程 LLM 化并强制输出**双方原文引文**；命中 E3/E4。
3. **语义相似度**（可选增强，BYOK 到 bigmodel 时）：embedding-3 双侧段嵌入+余弦矩阵，产出热力图证物（浏览器直连 CORS 已验证）；只做辅助展示，不参与判级（母项目经验：embedding 初筛假阳性率高，判级必须靠指纹）。

**独立复核（陪审团一致性）**：若用户配置了第二模型（不同供应商最佳），仅对指纹命中项做交叉复核——"这个指纹是巧合的风险有多大？"（移植 cross_check_llm2.py 的独立复核角色：复核模型不参与判级，只输出巧合风险评级+理由）。单模型配置时跳过并在判决书标注"未经独立复核"。

### 5.5 阶段五：宣判（Verdict）

1. 证据汇总 → 按 §4.2 阈值映射裁决词；
2. 生成**判决书**（结构化 JSON → 渲染，schema 继承 fact-check 项目的严格 JSON 输出模式）：
   - 案号（日期+输入哈希）、起诉状摘要（用户输入与案情画像）
   - 证据清单：每条=证据等级 / 目标引文 / 来源引文 / 来源 URL 与日期 / 复核意见
   - 群众线报栏、检索日志（查了什么、找到什么、排除什么）
   - 判决 + 法官意见（克制措辞的总结）+ 免责声明（固定文案）
3. **宣判动画**：判决锤 + 印章盖下（§8）；
4. 判决书可：导出独立 HTML（自包含，样式内联，可贴社区）/ 导出 JSON（复现用）/ 存入本地案件档案；
5. （M3 起）一键提交至公共案例库（GitHub PR 机制，人工审核后收录）。

### 5.6 降级链（内容不可得时的完整策略）

用户痛点：图书、视频、播客可能无网络资源或需付费。原则：**降级不拒判，但必须显式披露证据等级受限**。

| 场景 | 降级路径 | 裁决影响 |
|---|---|---|
| 播客无转录稿 | ① 用户粘贴转录稿 → ② PodScript/Apple 转录页链接 → ③ 仅 shownotes 比对 | ③ 的指纹数量大幅减少，多数走向「休庭」而非「卫生」 |
| 图书原文付费 | 基于公开书评/试读/出版社简介比对 | 判决书标注"证据等级受限：仅部分取证" |
| 视频无字幕 | ① 用户粘贴字幕 → ② 仅有简介时走 shownotes 同款降级 | 同上 |
| 候选源全文付费墙 | 用搜索摘要+片段做有限指纹验证 | 命中 E4 仍可判「不卫生」（单指纹极强），E3 需 ≥2 且标注局限 |
| 全程无任何候选源 | 「休庭」 | 明确"未发现≠清白" |

### 5.7 案件档案（Case Archive）

- localStorage 存全量案件（案卷+证据+判决）；导出/导入 JSON；
- 档案页=「判例集」：按裁决词筛选、按内容平台筛选、时间线视图；
- 与母项目 registry.json 的字段兼容（dscbl/sources/verdict/evidence_level/fingerprints），75 组历史对照可脚本转换为种子判例。

## 7. 技术架构

### 7.1 形态决策：v1 纯静态 BYOK，v2 按需加轻后端

依据今日实测（附录 A）：

- bigmodel chat/embeddings 端点**回显任意 Origin**（CORS 全开）→ 浏览器直连 LLM 可行 → v1 无服务器可行；
- r.jina.ai CORS `*` 且可穿透小宇宙页面（含评论）→ 浏览器直连取证可行；
- bigmodel ASR 端点 OPTIONS 405（无 CORS）→ 浏览器音频转录不可行 → v2；
- Tavily API 无 ACAO 头 → 浏览器直连搜索不可行 → 默认搜索走 GLM web_search 工具（同一 chat 调用，CORS 已通）。

```
v1（GitHub Pages，零成本）
  浏览器 SPA（React + Vite + TS，沿用 fact-check 技术栈与 BYOK 模式）
    ├─ 取证：r.jina.ai（无 Key 免费档；可配 Jina Key 提额）
    ├─ 分析/对质/宣判：用户自配 LLM（默认 GLM 系，直连；支持任意 OpenAI 兼容端点）
    ├─ 检索：GLM web_search 工具（默认） / s.jina.ai（选配）
    ├─ 语义相似（选配）：embedding-3 直连
    └─ 存储：localStorage 案件档案 + JSON 导入导出

v2（触发条件：音频转录需求 或 公共内置 Key 或 案例库上线）
  轻后端（Node/FastAPI 单进程，VPS 或 Cloudflare Workers）
    ├─ glm-asr-2512 多部分上传转录（移植 transcribe.py 的 ffmpeg 切片逻辑）
    ├─ 内置共享 Key + fact-check 式多层限流（1min/15min/1h 三档）
    ├─ 服务端 Tavily/Jina 搜索（绕开 CORS）
    └─ 案例库 API（SQLite/JSON in repo）
```

v1→v2 平滑性：前端供应商适配层统一抽象为 `chat / embed / search / fetch` 四个能力接口，后端只是新增一个"内置供应商"，前端代码零改动。

### 7.2 供应商适配层（G4 的落地）

```ts
interface ProviderAdapter {
  chat(req: ChatRequest): Promise<ChatResult>;      // 必配
  embed?(texts: string[]): Promise<number[][]>;      // 选配（P2 热力图）
  search?(q: string): Promise<SearchResult[]>;       // 选配（GLM web_search 或 Jina）
}
// 内置适配器：
// - glm.ts      —— bigmodel 原生（含 web_search 工具参数、embedding-3）
// - openai-compat.ts —— 任意 OpenAI 兼容端点（DeepSeek/Moonshot/OpenRouter/自建 vLLM），
//                        用户填 base_url + model + key，覆盖绝大多数"接入自己的模型"诉求
// - gemini.ts   —— Gemini 原生（OpenAI 兼容层亦可）
// Key 仅存 localStorage，任何网络请求不带埋点；页面明示"你的 Key 只从你的浏览器发出"
```

### 7.3 LLM 输出纪律（继承 fact-check 的严格 Schema 模式）

所有分析调用强制 JSON 输出（提示词内嵌 schema + 前端 JSON 宽松解析与一次重试）；判决书 schema 参考 fact-check 的 verdict/score/analysis/references 结构，扩展 fingerprints/evidence_level/cross_check 字段；语言一致性规则照搬（中文输入→全部中文输出）。

### 7.4 工程结构（预定）

```
health-court/

  src/
```

## 9. 数据、隐私与法律边界

- **本地优先**：v1 无任何自建服务器；案件数据只存用户浏览器；API Key 只存 localStorage 且仅从用户浏览器直连所配供应商；
- **最小引用原则**：证据卡片仅保存比对必需的引文片段（每条 ≤200 字级）+ 来源 URL + 抓取时间，不存全文（判决书导出 HTML 亦然）；
- **可删除**：案件档案与 Key 一键清空；
- **免责声明（固定文案，判决书与关于页双处）**：本产品输出为文本证据的自动化分析，非法律结论；"不卫生"等裁决词为游戏化表述，对应证据等级见判决书内说明；不对内容作者作动机推断；请读者依据材料自行判断；
- **对被核查内容的公平性**：判决书强制包含"核查范围与局限"栏（查了几个指纹、几个候选源、哪些内容未能取证），杜绝"没查到=没问题"的误导。

## 10. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| LLM 幻觉引文（编造来源引文） | 高 | 强制引文必须来自抓取全文的字符串定位（前端做子串校验，找不到即降级为"未定位"并告警）；双模型复核；判决书标注每条证据的取证方式 |
| 搜索召回不足导致漏判（假"卫生"） | 高 | 多轮检索策略+换词重试；「卫生」判决必须展示"已尝试的检索清单"；重要案件提示用户人工补充候选源 |
| GLM web_search 工具联调不确定性 | 中 | MVP 第一周做端到端验证；不可用则 s.jina.ai 顶上（需用户 Key）或降级为"仅对质用户提供的候选源" |
| Jina 免费档限流 | 中 | 前端节流+缓存；提示配 Key；v2 后端代理 |
| 被平台方（小宇宙等）反爬 | 中 | 走 r.jina.ai 渲染通道（当前可行）；引导用户粘贴正文作为终极回退 |
| 指控性内容引发法律纠纷 | 中 | §4.2 措辞红线+固定免责声明+最小引用原则+不存全文 |
| 免费模型能力不足影响对质质量 | 低 | 设置页对模型能力做分级提示（推荐 glm-4-flash 起步，强模型效果更好）；判决书记录所用模型 |
| 成本失控（用户 Key 被打爆） | 低 | 每案调用数预算（约 10–20 次 chat + 2–5 次抓取 + 3–6 次搜索）并在 UI 明示；前端限流 |
